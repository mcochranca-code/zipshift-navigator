# ZipShift database migrations

This directory contains source-controlled SQL migrations for schema changes that are applied to the managed MySQL database through the project migration workflow.

The `20260828_add_yellowbook_updated_by_role.sql` migration adds the nullable `yellowbook_encounters.updated_by_role` field. The API writes only the authenticated staff role (`admin` or `researcher`) from the server session; it never trusts a client-supplied attribution value and never stores a staff name in the patient summary card. When privacy mode is enabled, the UI intentionally renders the neutral label `Authorized staff`.

The `20260930_add_study_protocol_consent_foundation.sql` migration establishes the first research-governance boundary: studies, versioned protocol records, study memberships, versioned consent documents, participant consent decisions, and optional study/protocol links on referral cases. Apply it before using the administrator Research foundation panel or linking intake to research participation.

The `20261001_add_dictionary_instrument_manager.sql` migration adds versioned data dictionaries, variable definitions, research instruments, and instrument items. Dictionary variables and instrument items are editable only while their parent version is in `draft`; promote a version or create a new version rather than changing an active or retired definition.

The `20261002_add_care_coordination_portal.sql` migration adds optional specialist assignments on staff accounts plus care-coordination documents, typed acknowledgement signatures, and cross-team handoffs. These records are case-scoped and are separate from research-participation consent documents. The portal currently records an auditable typed acknowledgement; a legally binding electronic-signature workflow requires a separately reviewed e-signature integration.

The `20261003_add_intake_packet_library.sql` migration adds the official intake packet library, case-linked PDF metadata and managed-storage keys, file signature acknowledgements, packet assembly records, and a dedicated document audit trail. The original source PDFs are stored in managed storage and remain unmodified; completed case PDFs are uploaded through an authenticated specialist route, validated as PDFs, hashed with SHA-256, and served through short-lived signed download URLs. The current signing action is an auditable typed acknowledgement, not a legal e-signature certification.

The `20261005_add_esignature_canvas.sql` migration adds managed-storage metadata for the interactive signature canvas. Canvas signatures are captured as PNGs, SHA-256 hashed, linked to the case document signature, and recorded with a `PDF_SIGNED_WITH_CANVAS` audit event. This is an in-portal electronic signature capture with an accompanying typed acknowledgement; it should not be represented as a legally binding or regulatory e-signature without an approved e-signature provider and compliance review.

Case PDF controls use a strict `uploaded → review → signed` lifecycle. Specialist-role restrictions are enforced on both status changes and signature submission, signed and void documents are immutable, and voiding is recorded in the case document audit trail. The portal surfaces role-scoped reminders for pending privacy review and completed signatures; notification text avoids exposing document contents and reminds staff to verify minimum-necessary disclosure.

The `20261006_add_longitudinal_milestone_permissions.sql` migration adds `case_milestones` and an append-only `case_milestone_audit_events` ledger. Milestone writes are additive to the existing care portal and are permissioned as follows: administrators and care coordinators can manage all team milestones; an assigned SUD, Medical, Behavioral Health/Psych, Residential, Intake, or Peer Support specialist can manage milestones assigned to that team; researchers have read-only access; and other specialist teams cannot write or inspect another team’s restricted milestone. Open milestones can move through `in_progress`, `blocked`, `completed`, or `cancelled`; completed and cancelled records are immutable. Every create, update, completion, and cancellation also creates an existing `case_events` record for the broader timeline and notification system.

The `20261006_add_case_tasks_milestone_links.sql` migration adds a separate case-task queue linked optionally to a milestone. Task creation, status changes, completion, cancellation, and due dates are role-scoped to the assigned care team, append an existing case-event record, and synchronize an additive `task` milestone plus the specialist reminder stream. Existing referrals, handoffs, documents, signatures, and milestones remain available; tasks are an additional progress surface.

The attached `ZipShiftGuidedEntry_.pdf` is implemented as a public-facing Guided Access layer rather than a replacement for the Navigator. The new Start Here entry offers mode choice, progressive need/urgency/support questions, skip/unsure paths, adaptive presentation preferences, transparent “why this result” cards, and routes into the existing provider detail or county directory. It does not collect research consent or create a case by itself.

The `20261009_add_field_test_analytics.sql` migration adds a minimal event table for guided-start/completion/drop-off and resource-open/call/directions/website interactions. The client uses a locally generated opaque session key; no IP address, account ID, or free-text identity is stored. Admin and researcher reports return aggregate 30-day counts only. Provider detail cards now expose Spanish service descriptions plus available language and ADA/accessibility metadata, while the longitudinal task panel adds local filters for care team, due date, and urgency without changing the existing task API or workflow.

The website promo video is a deterministic 30-second 1920×1080 motion-graphics asset with exact readable messaging, ZipShift colors, resource-navigation scenes, care-coordination scenes, and a restrained ambient soundtrack. It is embedded additively on the Home screen as a native controls-enabled video; the reusable Python source is stored separately from the application bundle.

The `20261015_add_navigator_research_workflows.sql` migration adds additive `research_participant_controls` and `research_assessments` tables. Enrollment is study-scoped and requires an active granted consent; generated pseudonyms and assessment records exclude direct identifiers. Withdrawal marks participant and assessment records inactive, retention changes are auditable, and de-identified CSV exports are logged in `generated_reports`. The integrated researcher workspace now includes the existing-layout Navigator caseload with secure-chat, quiet-hours, FHIR-preview, and stage-advance actions; each meaningful action appends to the existing `case_events` ledger. The Research tab surfaces active protocol/consent versions, consent-gated enrollment, PHQ-9 and PRAPARE-aligned collection, item-9 safety flagging, assessment history, retention controls, withdrawal, and export without replacing the existing Cases, YellowBook, Reports, or Admin research foundation views.

Apply migrations before deploying code that reads or writes their fields, then verify the relevant columns and tables with `SHOW COLUMNS` / `SHOW TABLES`. Migrations are intended to be idempotent for MySQL environments that support `IF NOT EXISTS` clauses.

## 20261016 — Research and secure form completion additions

- Added `research_instruments.scoring_rules_json` so administrators can configure study-specific scoring bands and thresholds from the existing Data Dictionary & Instrument Manager.
- Added the integrated researcher participant timeline panel with assessment completion/score history and retention horizon visualization.
- Added role-scoped researcher notifications for retention deadlines, consent-version expiry (`consent_documents.expires_at`), and completed PHQ-9 records missing the safety item.
- Added `required_signer_roles_json` to care documents and managed signature integrity metadata (`signature_storage_key`, `signature_sha256`) for client/staff dual-signature online form sections. Legacy typed care acknowledgements remain supported; newly created online intake sections require client and staff signatures.
- Added secure online structured fill-and-sign popups to each official Intake Packet Library form without changing the source PDFs or removing the existing upload/review workflow.
- Added QR codes and directory last-verified dates to branded quick-guide PDF resource cards. QR codes resolve to the provider website when available, otherwise the provider address/name.
- Added additive Privacy & Consent and Research Consent launchers on the existing landing screen. They route clients to the profile/consent flow and staff, researchers, or administrators to their existing protected workspaces/sign-in boundaries.
